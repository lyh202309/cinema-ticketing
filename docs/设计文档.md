## 三、核心购票流程

```
热门场次（形态B·双阶段）：
  浏览影院/影片 → 选场次 → [1阶段]点"抢票" → Lua抢"资格名额"(计数器)
  → 抢到资格(前N名) → [2阶段]3分钟内选座 → 锁定座位 + 创建待支付订单(5分钟)
  → 5分钟内支付 → 出票(座位置已售)
  → 支付超时 → 释放座位 + 订单失效；资格超时 → 名额回流

普通场次（无秒杀，直接购票）：
  浏览 → 选场次 → 选座(可多选) → 锁定座位 + 创建待支付订单(5分钟)
  → 支付 → 出票；超时 → 释放；已支付可退票 → 座位释放回可售
```

## 四、待定决策 + 推荐结论

### 难点1：座位状态存储与锁座（结论已演进）
- **Redis 座位状态两态（0可售/1占用）就够**：座位图只看 0/非0、锁座判定只看 0/非0；"已锁 vs 已售"的区别由订单状态承担（竞态判定见下），前端不区分
- 存储结构：**bitmap 或 Hash 皆可**（内存差距可忽略，Hash 更好调试）；一个场次一个 key，field/bit=座位号
- 锁座：**Redis Lua 原子**（校验==0 → 置1），Redis 单线程保证并发下同一座位只有一个请求成功——两个候选方案共用这一步
- 已排除：全 DB（热点扛不住）、每座一个 key（MGET 慢）；三态(0/1/2)仅"Redis 主导"方案需要，非必须

### 难点2：锁座/订单 5 分钟超时释放（倾向定）
- **RabbitMQ 延迟队列**（TTL 300s + 死信交换机 DLX）：下单发延迟消息→到期进死信→消费者查订单仍待支付→释放座位+取消订单
- 资格超时（3 分钟）复用同一套延迟队列，不同 routing key
- 已排除：定时扫描（延迟大）、Redis 过期事件（不可靠）、Redis ZSet（本质轮询）

### 竞态判定：支付/取消原子互斥（讨论中，未定）
选座阶段（资格过滤后几百人量级）的支付/超时竞态，两个候选：

**候选A（DB 乐观锁，推荐）**：同步落库 + `UPDATE tb_order SET status=… WHERE status='待支付'` 判竞态
- 订单状态唯一真源在 DB，Redis 只是可重建的两态缓存；无双写、无最终一致
- 耦合：必须**同步落库**（DB 里要有订单才能乐观锁）
- 面试好讲：Redis 丢了从 DB 重建

**候选B（Redis Lua，用户方案）**：MQ 异步落库 + Redis 订单状态 Lua 原子转移（PENDING→PAID/CANCELLED）判竞态
- 风格统一全 Redis、性能上限高、展示 Lua 原子状态机
- 代价：Redis 订单状态 + DB 镜像**两份状态**，需解释最终一致性与 Redis 故障恢复
- 耦合：必须**异步落库**（DB 里暂无订单，只能在 Redis 判）

**关键认知**：同步落库⇄DB乐观锁、异步落库⇄Redis Lua 是**两套自洽组合，不可混搭**。
**资格过滤价值**：把 10 万并发压到几百，使选座阶段可用简单可靠的候选A。
**抢资格环节**：主链路 Redis Lua 原子扣名额（返回抢到/抢完/已抢过），无需 MQ；名额回流用 @Scheduled 定时扫描（对及时性不敏感）。

### 难点3：热门场次秒杀化形态 ✅已定
- **形态 B：双阶段**——第一阶段抢"资格"（Redis Lua 原子扣名额，**主链路无需 MQ**），第二阶段持资格用户限时选座
- **资格名额 = 座位数 × 3**（可调整），目的：保证票卖得完 + 削峰
- **双计时器设计**（核心）：
  - 资格计时器 **3min**：管"能否进选座页锁座"；资格到期 → 名额 INCR 回流（定时扫描，对及时性不敏感）
  - 订单计时器 **5min**：管"锁座后能否支付"；订单超时 → 释放座位（延迟队列）
  - 两计时器独立：资格到期**不影响已创建订单的支付**；但用户再回选座页换座会因资格失效而失败
- **名额回流做法 X（已定）**：资格到期即回流（无论是否锁座，3min 到即 INCR），周转快、实现简单
- 没抢到的人返回"服务器繁忙，稍后重试"，因 3 倍名额 + 回流，重试可能成功
- 形态 A（一套流程）、形态 C（前端排队）已排除

## 八、数据库表结构设计（草稿）

> 决策：座位**不建独立表**（由 hall 的 rows×cols 定义布局，占座记录在 tb_order_seat）；资格数据只存 Redis ZSet（不落库）；表贴合本项目、不照搬黑马点评。

### tb_user 用户
`id PK` / `phone`(唯一) / `password`(可空,验证码登录可无) / `nick_name` / `icon` / `create_time` / `update_time`

### tb_cinema 影院
`id PK` / `name` / `region`(区,筛选) / `address` / `rating DECIMAL(2,1)` / `phone` / `create_time` / `update_time`

### tb_hall 影厅（定义座位布局）
`id PK` / `cinema_id` / `name`("1号厅") / `rows` / `cols` / `create_time`

### tb_movie 电影
`id PK` / `title` / `genre` / `duration`(分钟) / `director` / `rating DECIMAL(2,1)` / `poster` / `release_date` / `description TEXT` / `status`(0未上映/1上映中/2下映) / `create_time` / `update_time`

### tb_session 场次（购票核心对象）
`id PK` / `movie_id` / `cinema_id`(冗余,按影院查) / `hall_id`(决定座位布局) / `start_time` / `end_time` / `price DECIMAL(10,2)`(统一票价) / `is_hot`(热门走抢资格) / `sale_start_time`(开售,热门=抢资格开启;普通场次可空=发布即可买) / **`sale_end_time`(截止售票,过它不再产生新订单;锁座前校验)** / `create_time` / `update_time`
- 座位总数 = hall.rows×hall.cols（不冗余）；Redis 座位状态 key = `seats:session:{id}`

### tb_order 订单（DB 真源）
`id PK` / `order_no`(唯一) / `user_id` / `session_id` / `total_price DECIMAL(10,2)` / `status`(**0待支付/1已支付/2已取消/3已退款**) / `create_time` / `pay_time` / `cancel_time` / `refund_time`
- 状态机靠乐观锁 `WHERE id=? AND user_id=? AND status=?` 转移（**所有变更都带 user_id 防越权**）

### tb_order_seat 订单座位（Redis 座位状态的对账依据）
`id PK` / `order_id` / `session_id`(冗余,按场次重建用) / `seat_row` / `seat_col` / `create_time`
- **不存座位状态**：已锁/已售/可售由 order.status 推导（待支付=锁/已支付=售/取消退款=可售）
- **不对 (session,row,col) 建唯一**：座位可多次出售、历史累积多行；"一时刻一座位只属一单"由 Redis Lua + 重建时按 status 过滤保证

### tb_chat_conversation AI 会话
`id PK` / `user_id` / `title`(首条摘要,会话列表显示) / `create_time` / `update_time`

### tb_chat_message AI 消息（永久存档）
`id PK` / `conversation_id`(索引) / `role`(0用户/1助手) / `content TEXT` / `create_time`

### 资格（不落库，纯 Redis ZSet）
`qualify:pool:{sessionId}`：member=userId，score=过期时间戳(抢到时刻+3min)；无独立名额计数器，ZCARD=已发数，抢资格 Lua 先清过期再判满
